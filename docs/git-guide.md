# Шпаргалка по Git для команды

Как мы работаем: **GitHub Flow**. Ветка `main` всегда рабочая, прямых пушей в неё нет. Любая задача делается в своей короткой ветке и попадает в `main` через Pull Request.

## 1. Один раз при настройке

**Вход в GitHub.** Пароль от аккаунта для Git не работает. Проще всего GitHub CLI:

```bash
gh auth login        # GitHub.com → HTTPS → Login with a web browser
gh auth setup-git
```

Либо войдите через IntelliJ: *Settings → Version Control → GitHub*.

**Клонирование проекта (один раз, если не сделали это при создании проекта):**

```bash
git clone https://github.com/vaib-devs/union-financial-aid.git
cd union-financial-aid
```

## 2. Ежедневный цикл работы над задачей
P.S. Вообще это не обязательно, и как правило всё это можно сделать в IDE нажатием на нужные кнопки, но если вы не знаете где и что, то используйте:
```bashIDE нажатием на
# 1. Обновить main
git switch main
git pull

# 2. Создать ветку под задачу (название Issue в имени)
git switch -c application-form

# 3. Работать, и время от времени сохранять
git status                       # что изменилось
git add путь/к/файлу             # "git add ." что бы добавить всё
git commit -m "feat: add application entity"

# 4. Отправить ветку на GitHub (первый раз с -u)
git push -u origin feature/12-application-form
# дальше просто: git push

# 5. Открыть Pull Request на GitHub, дождаться ревью и merge
```

**После merge:**

```bash
git switch main
git pull
git branch -d feature/12-application-form
```

Если `-d` говорит, что ветка «не влита» (из-за squash так бывает), а на GitHub PR точно смерджен, используйте `git branch -D`.


## 3. Основные команды

| Команда | Что делает |
|---|---|
| `git status` | что изменено, что в индексе, на какой я ветке |
| `git diff` | показать изменения, ещё не добавленные в индекс |
| `git diff --staged` | показать то, что попадёт в коммит |
| `git log --oneline -10` | последние 10 коммитов кратко |
| `git add файл` | добавить файл в следующий коммит |
| `git commit -m "..."` | создать коммит |
| `git switch ветка` | переключиться на ветку |
| `git switch -c ветка` | создать ветку и переключиться на неё |
| `git branch` | список локальных веток |
| `git fetch` | скачать новые данные с GitHub, ничего не меняя у себя |
| `git pull` | скачать и влить изменения текущей ветки |
| `git push` | отправить коммиты на GitHub |
| `git stash` / `git stash pop` | временно спрятать незакоммиченную работу / вернуть её |

**Перед каждым коммитом смотрите `git status`.** Убедитесь, что в списке нет лишнего: `.idea/`, `*.iml`, `target/`, `.env`, `uploads/`.

## 4. Подтянуть свежий `main` в свою ветку

Если ветка живёт больше пары дней, делайте это регулярно, чтобы конфликты были небольшими:

```bash
git switch main
git pull
git switch feature/12-application-form
git merge main
```

Если конфликтов нет, всё сольётся само, и остаётся сделать `git push`.

## 5. Конфликты слияния

Git не смог объединить правки одного и того же места и остановился. Это нормально и не поломка.

1. `git status` покажет файлы с пометкой *both modified*.
2. Откройте файл, там будут маркеры:
   ```
   <<<<<<< HEAD
   ваш вариант
   =======
   вариант из main
   >>>>>>> main
   ```
3. Оставьте нужный код (или объедините оба), **удалите строки с маркерами** `<<<<<<<`, `=======`, `>>>>>>>`.
4. Проверьте, что проект собирается.
5. Завершите:
   ```bash
   git add файл-с-конфликтом
   git commit          # сообщение о слиянии подставится само
   git push
   ```

Хотите отменить слияние и начать заново: `git merge --abort`.

В IntelliJ удобно: *Git → Resolve Conflicts* открывает окно с тремя колонками (ваше / чужое / результат). Если не уверены, что оставить, спросите автора второй правки, а не выбирайте наугад.

## 6. Что-то пошло не так: как откатить

| Ситуация | Решение |
|---|---|
| Изменил файл и хочу вернуть как было (ещё не коммитил) | `git restore файл` |
| Добавил в индекс лишнее (`git add`), но не коммитил | `git restore --staged файл` |
| Последний коммит с ошибкой в сообщении или забыл файл, **ещё не пушил** | `git add файл` → `git commit --amend` |
| Отменить последний коммит, но оставить изменения в файлах (**не пушил**) | `git reset --soft HEAD~1` |
| Отменить уже запушенный коммит | `git revert <хеш-коммита>` (создаст новый коммит-отмену, историю не ломает) |
| Нужно срочно переключиться, а текущая работа не готова | `git stash`, переключиться, потом `git stash pop` |

**Не используйте** `git push --force` и `git reset --hard` в общих ветках, если не понимаете последствий: можно потерять чужую работу. При сомнениях сначала спросите тимлида.

## 7. Частые ситуации

**Закоммитил в `main` вместо своей ветки (и ещё не запушил):**
```bash
git switch -c feature/мое-имя-ветки      # коммиты остаются на новой ветке
git switch main
git reset --hard origin/main             # main возвращается к состоянию на GitHub
git switch feature/мое-имя-ветки
```

**`git push` отклонён (`rejected`, `non-fast-forward`).** На GitHub в этой ветке есть коммиты, которых нет у вас. Сделайте `git pull`, решите конфликты, если они есть, и повторите `git push`.

**`detached HEAD`.** Вы смотрите конкретный коммит, а не ветку. Просто вернитесь: `git switch имя-ветки`.

**Забыл создать ветку и уже правил файлы (ничего не коммитил):** `git switch -c feature/название`, изменения переедут вместе с вами.

**Случайно закоммитили секрет (пароль, токен, реальные паспортные данные), даже если ещё не пушили.** Скажите тимлиду. Если секрет уже попал на GitHub, считайте его скомпрометированным: смените пароль или токен. Простое удаление файла новым коммитом ситуацию не исправляет, потому что секрет остаётся в истории.

**Хочу посмотреть, что изменилось в чужой ветке/PR:** `git fetch`, затем `git switch имя-ветки`.

## 8. Что нельзя коммитить

- Пароли, токены, файл `.env` (в репозитории только `.env.example`).
- Реальные персональные данные: паспорта, ИНН, счета, фото документов. В тестах только выдуманные данные.
- Папки `.idea/`, `target/`, `node_modules/`, файлы `*.iml`, загруженные файлы из `uploads/`.
- Огромные бинарные файлы.

## 9. Золотые правила

1. Начинай любую задачу с `git switch main` и `git pull`.
2. Одна задача, одна ветка, один PR.
3. Коммить часто, пушь, как минимум, в конце рабочего дня: работа, лежащая только на вашем компьютере, под угрозой.
4. Перед `git add .` смотри `git status`.
5. Не пушь в `main` напрямую и не используй `--force`.
6. Не уверен, спроси, прежде чем выполнять команды с `reset --hard` или `--force`.
